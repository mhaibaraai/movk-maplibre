## Introduction

`MaplibreLayerGroup` groups several child [MaplibreLayer](/docs/core/layer) components and is the single source of truth for layer management:

- **Stacking order**: `zIndex` orders the group among its siblings, higher on top, independent of mount order.
- **Insertion anchor**: `beforeId` places the group's layers below an external layer such as the basemap, given a layer id or a predicate, inherited from the parent group when unset.
- **Visibility and opacity**: `v-model:visible` and `v-model:opacity` apply to every layer in the group. Hiding the group takes precedence over each layer's own `layout.visibility`; opacity scales the opacity properties of each layer type and multiplies with the layer's own values.
- **Nesting**: nested groups combine visibility with AND and multiply opacity.
- **Layer tree**: with a `title`, the group appears in [MaplibreLayerControl](/docs/controls/layer-control), [MaplibreLegend](/docs/controls/legend) and [useLayerTree](/docs/composables/use-layer-tree), all of which read and write this group's `v-model`.
- **Basemap layers**: the `styleLayers` predicate brings layers that ship with the basemap style (labels, roads and so on) under the group's control.

::note
Opacity expressions driven by zoom (`interpolate` / `step` with `zoom` input) are scaled output by output; expressions that cannot be scaled safely, such as `zoom` used below the top level, keep their value and log a warning.
::

### Control basemap layers

`styleLayers` matches layers that ship with the basemap style by their traits (type, `source-layer` and so on) rather than hard-coded ids, so it keeps working with another style:

- Only layers present when the style loads are matched; business layers added at runtime are unaffected even if they fit the predicate.
- After a basemap switch the group matches the new style again and reapplies its state.
- When the group unmounts, adopted layers return to their original visibility and opacity.

Colors of such layers are mostly zoom-driven expressions, so the derived legend is meaningless; set `:legend="[]"` in most cases.

::note
On raster basemaps (such as [Tianditu](/docs/extensions/tianditu)) the annotation is a separate raster layer and must be matched by layer id; features drawn into the basemap tiles, such as roads, cannot be split out.
::

### Layer order

`zIndex` (also usable as `v-model:z-index`) stacks higher groups on top; ties go to the later-mounted group. Each map keeps a layer stack that computes the insertion position from sort keys, so mount order, late-arriving data, `v-if` remounts and basemap switches never change the final order, and changing several groups in one tick reorders only once. Layers of a group stay contiguous, nested groups are ordered as a whole inside their parent, and child layers can set their own `zIndex` to order within the group.

### Below basemap labels

`beforeId` positions layers relative to external layers such as the basemap. Besides a layer id it accepts a predicate: the first matching layer shipped with the basemap style becomes the anchor, it is re-resolved after a basemap switch, and layers go to the top when nothing matches.

---

::

::tip
Define the predicate in script; an inline predicate in the template is a new function on every render and triggers an order check each time. Express order between managed layers with `zIndex`; anchoring `beforeId` to another managed layer only guarantees being below it, not directly below it.
::
